# 总体路线图与实现协议

## 1. 目标和边界

本路线图追求的是“让项目承诺可验证”，不是统一六个仓库的技术栈。六个仓库的生命周期不同，不能强行共享一套构建脚本、目录布局或发布流程。

本轮设计覆盖：

- 对外文件格式和 CLI 契约；
- 数据安全、失败原子性和资源边界；
- 可复现环境、参考实现一致性；
- 与风险相匹配的 CI 和发布门禁；
- 组织名称、仓库状态和文档真实性。

本轮明确不做：

- 将 C++ FQC 与 Rust FQC 合并成一个代码库；
- 为所有项目引入统一框架或统一语言；
- 仅因单文件较大而拆分 `fq-compressor/src/format/archive.cpp`；
- 为 compress-kit 建立复杂的长期兼容层；
- 在 MICOS 的每个 PR 中构建全部大型生信镜像；
- 对 fastq-tools 已经成熟的脚本体系做无证据的全面重写。

## 2. 风险排序

### P0：先阻断契约冲突和数据风险

| ID | 风险 | 后果 | 对应设计 |
|---|---|---|---|
| `FQC-FAMILY-001` | 两个格式族共享 `fqc/.fqc`，但跨族识别契约尚未固定 | 用户调用错误实现时只得到含糊错误，容易误判损坏 | 01 |
| `FQCR-SPEC-001` | Rust 规范与实际字节编号冲突 | 第三方实现依据文档生成不可读文件 | 02 |
| `FQCR-IO-001` | Rust 直接写最终输出路径 | 失败后留下部分文件，覆盖时可能丢失旧结果 | 02 |
| `CK-DEC-001` | 不兼容格式沿用旧 magic | 新旧文件不可可靠区分 | 05 |
| `MBW-CI-001` | parity 测试在 CI 静默跳过 | “与 C 一致”的核心承诺没有被验证 | 04 |

| ID | 风险 | 后果 | 对应设计 |

## 3. 推荐实施波次

### Wave 0：负责人决策（已完成）

1. `FQC-DEC-001`：两个实现都保留 `fqc/.fqc`，依靠不同 magic 区分格式族；
2. `CK-DEC-001`：采用四个 v2 magic，拒绝 v1，发布 `2.0.0`；
3. `MICOS-ORCH-001`：Python CLI 是唯一生产入口，WDL 当前为实验性；
4. `ORG-GOV-001`：六个子仓库分别保存自己的 OpenSpec artifacts，根目录不初始化 Git。

仍需为每个仓库指定最终评审人。以上决策应由首个相关 change 固化到仓库内规范；根目录聊天记录不是长期事实源。

### Wave 1：让文字与现状一致

优先修正文档中的事实错误，但不伪装未来能力已经存在：

- Rust FQC 的 codec/checksum 编号和兼容性声明；
- C++ FQC 的 `verify` 实际为完整解码校验；
- MICOS 配置中尚未生效的参数，以及 Python/WDL 状态；
- compress-kit 的大小限制与破坏性变更说明；
- minibwa-rust 的真实 parity 前提和里程碑状态；
- fastq-tools 的 CPU 最低要求和发布状态。

### Wave 2：先添加失败测试和冻结样本

所有二进制格式修改必须先有能证明旧行为的测试：

- 每个格式至少一个最小合法文件、一个典型文件、一个损坏文件；
- fixture 必须记录生成器版本、生成命令、输入哈希和预期行为；
- 对压缩器输出易受第三方库版本影响的部分，不比较整文件哈希；应断言稳定的结构字段，并用冻结文件验证解码兼容性；
- 测试必须能够在 CI 环境确定性运行，不能因依赖缺失直接返回成功。

### Wave 3：安全和格式实现

在测试保护下实施：

- Rust FQC 原子输出、解压资源上限、header codec 的真实分派；
- compress-kit v2 magic 与清晰的旧版本错误；
- minibwa-rust 固定 C 参考提交并强制 parity；
- MICOS 单一生产编排和 run manifest；
- fastq-tools 可移植发布基线。

### Wave 4：CI、发布和元数据

最后把已经能在本地稳定执行的校验接入 CI，再处理组织名称、徽章、发布说明和生命周期标记。CI 不应成为第一次发现测试无法运行的地方。

## 4. 任务规格模板

后续实现模型必须按“仓库内 change ID + 设计任务 ID”工作。change artifacts 的完整约定见 [10-repository-local-openspec-workflow.md](10-repository-local-openspec-workflow.md)。每项任务应具有以下字段：

| 字段 | 解释 |
|---|---|
| 状态 | decision 的 `Accepted/Superseded`，或 change 的生命周期状态 |
| 目标 | 完成后可观察到的结果 |
| 前置条件 | 必须先批准或完成的任务 |
| 允许修改 | 本任务可以触碰的文件或目录 |
| 实施要求 | 必须实现的行为，不限定不必要的内部写法 |
| 验收条件 | 可由评审者独立核验的结果 |
| 验证命令 | 仓库标准命令和必要的专项测试 |
| 非目标 | 防止实现模型扩大范围 |

如果任务执行中发现规格错误，应停止在最小可验证状态，提交证据和建议，不要自行改变外部产品决策。

## 5. 实现模型工作协议

### 5.1 开始前

1. 确认当前目录是目标独立仓库，而不是工作区根目录；
2. 完整阅读该仓库的 `AGENTS.md`；
3. 检查 `git status --short`，保留所有已有修改；
4. 只领取一个 Approved change，并核对其关联任务 ID；
5. 检查所有前置决策是否已有明确批准记录；
6. 先运行与任务相关的最小基线测试，记录现有失败。

### 5.2 实施中

- 不进行顺手重命名、全局格式化或无关依赖升级；
- 不为已知类型堆叠 `getattr`、`isinstance`、宽泛 `try/except` 等防御性噪声；
- 不为未来假设添加未使用的抽象层、公共 API 或配置项；
- 修改外部格式时，解析器的错误必须可区分：版本不支持、文件截断、校验失败、资源限制；
- 修改 CI 时，失败不能被 `|| true`、静默 skip 或仅打印警告掩盖；
- 不跨仓库复制未审查的实现。跨仓库只共享契约说明和测试向量。

### 5.3 完成报告

实现模型必须报告：

1. change ID、关联任务 ID 和采用的决策值；
2. 修改文件清单；
3. 行为变化和兼容性影响；
4. 执行过的完整验证命令及退出状态；
5. 未执行的验证及原因；
6. 剩余风险；
7. `git diff --check` 和最终 `git status --short` 结果。

不得自动归档、提交、推送、创建 PR 或发布，除非对应门禁满足且负责人另行授权相关动作。

## 6. 统一完成定义

一项任务只有同时满足以下条件才算完成：

- 代码行为与公开文档一致；
- 新行为有正向和失败路径测试；
- 原有测试通过；
- 格式/静态检查通过；
- 对外契约变化写入 changelog 或 ADR；
- 没有把失败降级成 skip；
- 没有引入与任务无关的 diff；
- 评审者能够只根据任务文档复现验收结果。

## 7. 决策记录格式

建议把批准结果放入相关仓库 change 的 `design.md`，归档后由主规格保存最终规则。复杂且长期有效的架构决定可以另存 `docs/adr/YYYY-MM-DD-<topic>.md`：

```markdown
# 决策标题

- 状态：Accepted / Rejected / Superseded
- 日期：YYYY-MM-DD
- 负责人：姓名或 GitHub ID
- 关联任务：TASK-ID

## 背景
## 决策
## 被否决方案
## 兼容性与迁移影响
## 生效版本
```

口头选择或聊天中的模糊同意不应作为破坏性格式变更的唯一依据。
